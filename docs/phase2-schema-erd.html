Trials Data Model

Relational schema for REEC study data, drawn from what the list (estudios/getestudios) and detail (detalle/{id}) endpoints actually return, cross-checked against the official AEMPS manual (docs/Manual-Interaccion- REEC-Servicio-Extraccion-Datos-v1.pdf). Scoped generously — every structured field REEC gives us gets a column, not only the ones the current analysis questions require.

15 tables studies carries 58 columns across 4 groups 6 many-to-many bridges Not yet built — review before db/schema.sql

Entity relationships

studies is the hub. Sponsors own studies one-to-many (REEC only ever records one promotor per study — confirmed by checking the raw type, not assumed). Centers, therapeutic areas, and funders are each many-to-many with studies, so each gets a bridge table. Interventions belong to exactly one study — but three of their own fields (substances, ATC codes, administration routes) are themselves pipe-delimited lists, so the same many-to-many pattern repeats one level down.

primary key foreign key derived at load time (not a raw field) inferred meaning, not confirmed by a source deliberately excluded from schema

Scope: minimum, not ceiling

§3.3 of PROJECT_SPEC.md lists volume, therapeutic landscape, phase, sponsor, geography, duration, and results-compliance as the analysis questions. Those are a starting set, not the full scope — this schema keeps essentially every structured field REEC returns (population by sex/ age/vulnerability, purpose/objective flags, data-source flags) even where no §3.3 question uses it yet, so a new question later doesn't require re-ingesting or re-designing.

Only three categories are cut, and for a specific reason each — see Excluded fields below.

Why six bridge tables, not six text columns

sustancias, atcs, viasAdministracion, and organismo.financiador all arrive from REEC as pipe-delimited strings (e.g. "Amgen|AstraZeneca AB") — one column secretly holding a list. Left as text, "how many trials did AstraZeneca fund?" needs a LIKE string match instead of a JOIN. Checked rather than assumed, on the 2019 cohort (629 studies):

financiador → 602 single-funder · 27 (4.3%) multi-funder — real co-funding, not a formatting artifact

Same shape as centers: whenever both "can one study/ intervention have several?" and "can one value apply to several studies/interventions?" are yes, it's many-to-many and gets a lookup table + bridge, not a delimited column.

PKdepartamentotext, not null — see notebelongs here, not on centers — checked empirically: of 361 distinct center referencias across the 2019–2020 files, 245 (68%) show more than one distinct (departamento, investigador) pair across different studies. Same hospital, different department per trial — it describes the pairing, not the center. Kept as plain text: raw values are inconsistent free text ("Oncología" / "ONCOLOGY" / "Servicio de Oncología Médica" for what's presumably the same thing), so a normalized lookup wouldn't yet support reliable grouping — same reasoning as excluding the free-text informacion fields.

Why departamento is in the key, not just a column: checked whether the same (study, center) pair can have more than one department — it can. 4,398 of 11,700 studies-with-centers (37.6%) repeat the same center within one study under a different department (e.g. a hospital running one trial through both Endocrinología and Cardiología). A 2-column key (study_id, center_id) would wrongly reject the second department as a duplicate, so the key has to include departamento too.

Loader must coalesce blank department to '', never NULL: SQL treats every NULL as distinct from every other NULL for uniqueness purposes — NULL = NULL is unknown, not true — so two blank-department rows for the same study+center would silently both be kept instead of collapsing into one, quietly defeating the point of the 3-column key for exactly the rows where department is unknown. departamento.strip() or '' at load time, not None.

Excluded fields

Three categories are cut on purpose — everything else structured stays in:

  • Free text — the 22 informacion fields (×2 languages: titles, indications, inclusion/exclusion criteria, endpoints). ~80% of the detail payload's bytes, but unstructured — would need NLP to use, and feeds no current or reasonably-anticipated analysis question. (It's also what let us sanity-check mujerusa above — worth keeping in the raw cache even though it's out of the schema.)
  • Named-individual privacy — organismo.mail, organismo.telefono, organismo.personaContacto, and centros.centro[].investigador (confirmed live: real principal-investigator names, e.g. "Ebymar Arismendi Núñez" — same category as personaContacto, not a role or department). Public by legal mandate, so caching them locally is fine, but per §3.2b they must not reach the DB or the deployed dashboard.
  • Two dead calendario fields — fechaFinPrevista and fechaClasificacion, both 0% filled in every cohort sampled (§3.2).
